# ADR 0001：审批动作、事务回执与显式恢复

- 状态：采用（归纳 Day 15–20 已有实现，Day 21 未改变业务行为）
- 日期：2026-11-16
- 复核代码基线：1f95ff5f00200b6e761afca7b1ec57d86f8422dd

## 背景

模型只应提出动作。批准可能重发，HTTP 响应可能丢失，进程可能在节点完成和检查点保存之间退出。恢复执行路径本身不能保证副作用只发生一次。

## 决策

1. 审批持久绑定主体、租户、run、精确动作参数摘要及期限。模型输出与 LangGraph Command 仅提出或唤醒工作，不能证明授权；决定接口与执行节点重新读取数据库的可信记录。
2. 同一建单动作使用审批 UUID 派生的 key。对审批行加事务锁，动作执行回执有租户/key 唯一约束；工单、审批 executed 状态和回执同库同事务提交。重试校验身份与摘要后返回保存的结果快照。
3. PostgreSQL 保存图检查点和运行归属，恢复由显式请求驱动。运行级 advisory lock 避免同一 run 并发执行；不把检查点当作审批依据，也不把状态 running 当成进程仍存活的证明。
4. 重试只开放明确的暂时错误类别，并受尝试数与调用预算约束。权限、参数、额度错误停止；写操作始终复用原审批 key，不生成新逻辑动作。

## 取舍与后果

- 保留当前单库部署，减少跨系统事务范围；没有引入消息队列、分布式锁服务或新编排框架。
- 原生循环保留为教学对照，图复用步骤逻辑。持久化增加迁移、schema 与生命周期管理成本。
- 回执是执行时的结果快照，当前工单状态应另行读取。新审批意味着新动作；不做跨 run 的文本去重。
- 线程超时后工作可能继续，进程中断后的节点可能重放。同库事务保护本项目副作用；接入外部写服务时需要对方的幂等协议或补偿设计，本日不预先引入。
- 隔离测试 schema 需要专用 `_test` 库及相应权限。演示使用固定本机身份，不代表生产权限闭环已完成。
