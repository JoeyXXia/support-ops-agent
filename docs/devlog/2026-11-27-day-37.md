# Day37 · 有限并发、取消与积压

北京时间 2026-11-27。开工时本地与 GitHub main 均为 `7d36657`。Day36 已将执行移到独立 PostgreSQL worker，具备租约和检查点，但队列可持续增长，也没有所有者取消或单轮执行时限。

## 三组改动

1. `packages/agent/run_queue.py` 和 `apps/api/worker.py` 增加数据库事务内的容量准入与 worker 有界并发。Compose 暴露配置，延续单进程部署。
2. 新增 `0009_run_limits` 迁移、运行取消 API 和操作边界检查。更改涉及运行持久化、图操作调用点、审批重入队、工单执行与前端终态映射。已提交动作仍由持久回执提供证据。
3. `tests/integration/test_run_limits.py` 增加四项专项，README、范围文档和 JSON 记录部署、证据和限制。

## 五项可观察验收

- 同账号第二条任务在测试阈值 1 时返回 429。另一账号填满测试阈值 2 时，第三账号返回 503。取消排队任务后容量可用。
- 在并发设为 2 时，已进入模型的两个任务阻塞，第三个等待，前两个释放后第三个才开始。
- 非所有者取消返回 404。排队任务取消后状态为 `cancelled`，恢复请求保留该状态。
- 工具执行中请求取消或用数据库夹具使时限过期，当前工具有完成事件，第二个工具没有启动。分别得到 `cancelled_by_owner` 和 `failed/run_timeout`。
- 已提交工单以及幂等回执仍可查询，取消后的新工单写入被拒绝。

最易失败的边界是取消发生在工单事务提交前后。准入使用 PostgreSQL 事务锁保证计数与入队一致，工单写入在同一事务内检查运行并保留既有回执回放。运行时限以数据库为准，从本轮首次领取开始，租约恢复不延长，审批后重新入队开启新一轮。取消采用协作式检查，正在执行的操作可以结束。前端显示取消终态，本轮取消动作走 API。
