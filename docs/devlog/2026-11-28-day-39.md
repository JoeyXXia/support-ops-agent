# Day39 · Trace 与故障定位

北京时间 2026-11-28，手动推进一天。开工时本地和 GitHub main 均为 `ee2e7a5`。Day38 已支持事件快照重放，运行详情可以回显动作，却缺少跨 API、worker 和数据库的统一关联信息及耗时。

## 三组可独立审查的改动

1. `packages/agent/trace.py`、现有 API 与 worker 为 HTTP 请求生成 UUID，运行保存初始请求 ID，步骤用运行 ID 加步骤号关联。分别计时模型、检索、工具、审批、写入及关键数据库操作。运行详情显示请求 ID 和步骤耗时。
2. `GET /runs/{run_id}/trace` 复用所有者访问控制，返回脱敏事件、失败步骤与持久回执状态。故障夹具覆盖工具失败无写入、工单提交后响应失败。
3. 验证报告和故障手册记录证据、复现命令和限制。沿用现有日志与数据库。

## 五项可观察验收

- 服务端生成 HTTP 请求 ID，不接受客户端同名头覆盖。创建请求 ID 在运行记录、worker 日志和步骤事件能关联。
- 模型、检索、工具、审批与数据库均产出非负实测耗时，页面保留可理解的事件描述。
- 同一失败 run ID 可查询步骤、类别与工单回执；其他用户查询返回 404。
- 工具失败显示第 1 步、`not_found`、无工单回执。数据库已提交而 worker 响应失败时，诊断仍显示已提交回执。
- 注入原始问题、错误消息和请求头的合成标记不出现在结构化日志或诊断输出中。已有回归通过。

主要风险是把运行终态误读成工单事务状态。本次以独立的 PostgreSQL 执行回执为证据，并保留失败步骤为空的可能。每次模型或工具尝试分别计时，数据限于本地合成负载。端点查询耗时不代表人工排障耗时。

## 实测

- 最终 PostgreSQL 专项 2 项通过（2.662 秒），全量 60 项通过（70.683 秒）。两个已知失败 run 的诊断请求在专项为 12、10 ms，在全量复跑为 11、9 ms。这些数字是本机诊断端点的测量。
- Python 离线 127 项通过（52.028 秒）。前端 9 项测试、格式和类型检查通过，Compose 配置检查通过。
- 首轮离线回归有两处事件全文比较因耗时浮动失败。把事件耗时限于有关联运行 ID 的执行后，独立调用保留确定性，两种执行路径兼容。
- 合成故障覆盖工具不可读取与工单事务提交后的响应失败。两者均使用真实 PostgreSQL 持久状态和 mock 模型，真实模型请求 0 次。
