# Day38 · SSE 重连与事件恢复

北京时间 2026-11-28，手动推进一个 Day。开工时本地和 GitHub main 均为 `9867d67`。Day37 已实现持久任务与运行终态。原 SSE 序号按连接重置，服务端拒绝 `Last-Event-ID`，网络中断后页面需要手动重新查询。

## 三组可独立审查的改动

1. `0010_run_event_replay`、`packages/agent/run_snapshots.py`、`apps/api/events.py` 及 worker。PostgreSQL 在运行记录事务内保存同一 run 的递增快照。每个快照包含截至当时的事件列表，连接重建时按游标重放，不额外调度任务。保留期 24 小时，worker 分批清理。
2. `apps/web/src/App.tsx` 与 `runEvents.ts`。网络中断由原生 EventSource 携带上一次序号重连，同一连接周期保留去重水位。重放快照整体替换当前事件与结果。已完成、失败、停止和取消的终态不会被迟到帧覆盖。刷新通过原运行 ID 恢复。
3. PostgreSQL 与 Chromium 回归、README、范围和实测报告。验证正常重放、过期、回滚、权限、工单去重及刷新。

## 五项可观察验收

- 携带有效游标时仅重放之后的快照，稳定递增。最新终态允许同序号回送以关闭连接。非法游标返回 400，非所有者返回 404。
- 快照和运行更新一起提交或回滚。清理超出保留期的快照后，过期游标用当前权威记录恢复，运行记录保留。
- 浏览器收到一个真实 SSE 帧后模拟连接断开。后续请求携带该帧的 `Last-Event-ID`，同一 run 无额外提交。
- 批准后刷新保留原 run ID 和工单 ID，页面只显示一个工单入口。重复或迟到帧不能使终态回到运行中。
- 已有知识引用、审批、工单幂等与 PostgreSQL 迁移回归继续通过。

最易失败的边界是游标指向过期记录、审批前一阶段的迟到帧和刷新时的重复提交。重放以快照为单位，应用可以直接从权威记录修复缺口。审批中间快照不会提前关闭当前连接。内存模式继续使用连接级序号。24 小时限制针对重放历史，运行详情仍按原规则保留。

## 实测

- PostgreSQL 迁移和 SSE 专项 2 项通过（2.180 秒），全量 58 项通过（70.638 秒）。在合成工单上验证了游标连续、回滚后序号未变、终态回送、过期后权威快照恢复及单一工单。
- Python 离线 127 项通过（53.399 秒）。前端 9 项测试、格式及类型检查通过。
- 真实 Chromium 端到端 4 项通过（11.0 秒）。断流测试单项 4.4 秒，浏览器携带首帧的 `Last-Event-ID` 重连，刷新后仍是同一运行与同一工单，整个流程仅提交 1 次运行。
- 首两轮浏览器夹具持续拦截 SSE 请求，未能在路由事件读出重连头，虽然页面已恢复。拦截只用于首个响应后，未拦截的请求可观察到期望的头。相关行为见 [Playwright 网络拦截说明](https://playwright.dev/docs/network#how-request-interception-works)。真实模型调用为 0。
