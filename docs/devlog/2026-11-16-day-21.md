## 五项可观察验收

- 提案后 run 为 awaiting_approval，审批为 pending，工单与回执数量均为 0；未批准执行返回 409。
- 批准后同一 run 完成，reason 为 ticket_created，审批为 executed，数据库恰有一张工单和一条执行回执。
- 重复批准并重复执行 3 轮，批准返回 202、执行返回 201，回执一致，计数仍为 1/1。
- after-tools 故障点真实终止子进程；新进程 show 后以原 run ID resume，完成且保存模型/工具计数为 2/2，没有新增工单。
- 打开离线 HTML 可按顺序看到全部 9 步的原始状态、返回值和计数，不依赖讲解者补充隐藏结果。相关审批、检查点、幂等和写重试回归通过；具体数量、耗时和原始输出以验证 JSON 为准。

以上业务演示已实测。JSON 保存实测观察，HTML 是这些观察的浏览器回放，**不是业务页面录屏，也不是网络端到端验证**。模型始终为确定性 mock；数据库与进程故障是真实的。没有调用付费 API。

1. 按 docs/database.md 准备既有 PostgreSQL/pgvector 与专用 `_test` 库，设置显式 `TEST_DATABASE_URL`，不得指向业务库。凭据只放忽略的本地环境配置。

3. 浏览器打开 reports/day-21-demo.html。顶部明确说明 mock、真实数据库、ASGI 与回放性质。JSON 是可独立核查的原始步骤。
4. `python scripts/check_offline.py`；设置 TEST_DATABASE_URL 后，分别执行 `python -m unittest discover -s tests/integration -p test_approvals.py -v`，以及 test_checkpoints.py、test_idempotency.py、test_write_retry.py。命令结果见 reports/day-21-validation.json。

## 最可能失败的边界

- 数据库不可用、错误的测试库名或迁移失败：停止演示，不退回 SQLite，不把失败写成完成。schema 清理失败也不会交付成功记录。
- 进程启动或故障点未到达：30 秒内失败并结束本次创建的子进程，不杀其他服务。恢复命令也有明确超时。
- 节点执行后尚未保存检查点就退出，恢复可以再次执行节点。保存的调用计数不代表外部服务精确计费。恢复不等于永不重复执行。
- 相同审批/key 的重试才复用回执；新 run 生成新审批可合法创建另一张工单，不能用“同样文字”推断同一动作。
- 当前身份仍是本机演示身份；ASGI 录制不验证浏览器跨域、网络断开、生产认证或真实模型质量。审批过期、参数变化、权限拒绝等边界由相关回归覆盖，不在回放中冒充新增实测场景。

## 讲解与追问

问：为什么重复批准没重复建单？批准只是保存可信决定；执行重新检查审批归属和参数，用审批派生的 key 读取或提交执行回执，工单、审批状态和回执在同一事务内变化。

问：为什么既有锁又有唯一约束？行锁让同一审批串行执行，唯一约束是最终数据库不变量；进程内锁无法保护另一个进程。

问：死锁怎么办？仅明确的临时 SQLSTATE 在预算内重试；每次失败事务先回滚，重试复用相同逻辑动作，不能把权限错误也当死锁。

问：恢复会重复副作用吗？节点可能重放，外部副作用必须另有幂等协议。本项目建单通过同库原子事务与回执保护；不据此声称任意外部服务 exactly-once。

里程碑 `v0.3-actions` 只代表本地合成场景的审批、幂等与恢复工程演示，不包含 Day 22 认证，也不代表真实模型验收完成。
