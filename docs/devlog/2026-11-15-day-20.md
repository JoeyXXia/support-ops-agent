## 当前实现与最小方案

此前原生循环和图已有单次超时、6 个逻辑步与工具预算，模型适配器已经区分临时限流和额度耗尽。运行层直接结束失败请求，尚未统一退避和重试。Day 19 已提供相同审批 key 的执行回执，为受控写入重试提供基础。

三个审查单元如下。

1. 策略与分类。新增 `packages/agent/retry.py`。ProviderError 同时通过已知临时错误类别与 retryable 标记才允许重试。数据库只对明确的连接、序列化和死锁错误开放重试，权限及参数错误停止。策略默认最多尝试 3 次，退避为 0.1、0.2 秒。
2. 运行与预算。`packages/agent/loop.py` 共用模型和工具的有界调用逻辑，`graph.py` 接入受控写入。`packages/tools/executor.py`、`schemas.py` 传递暂时错误分类。新增逻辑 steps 与 write_calls，model_calls、tool_calls 计入失败尝试。默认预算为 6 个逻辑步、8 次模型尝试、8 次工具尝试，写入尝试最多 3 次。图保留节点递归上限，旧检查点缺少 steps 时由原 model_calls 恢复逻辑步数。
3. 验收与展示。新增 `tests/test_retry.py`、`tests/integration/test_write_retry.py`，`apps/web/src/App.tsx` 展示错误、退避和停止原因及计数。日志包含 attempt、retryable、delay_seconds 和运行累计计数。README、scope 与验证 JSON 记录实测结果。

## 错误决策表

| 错误 | 运行层决定 |
| --- | --- |
| 模型 timeout、临时 rate_limit、connection、upstream，且 retryable 为真 | 在尝试次数和调用预算内退避后重试 |
| authentication、permission、invalid_request、quota_exhausted、无效输出 | 一次失败后结束 |
| 工具 forbidden、invalid_arguments、not_found、unknown_tool | 一次失败后结束 |
| 允许的工具返回暂时 timeout、rate_limit、unavailable | 在工具尝试预算内重试 |
| SQLSTATE 40001、40P01、08 类连接错误 | 对许可动作开放重试 |
| SQLSTATE 42501、22 类数据错误 | 按权限或参数错误停止 |
| 未识别异常 | 记录脱敏的 internal_error 并停止 |

工具重试白名单包含现有读取工具与绑定 run 的 propose_ticket。草稿复用原 run 与精确参数，建单 execute 复用原审批、idempotency_key 和摘要。模型工具列表仍由注册表决定，重试策略由服务器执行。

## 五项验收与实测

- 模型临时失败后可以继续完成原逻辑步骤，原生循环和 LangGraph 的步骤计数一致。持续限流尝试 3 次后结束，退避顺序为 0.1、0.2 秒，最后一条 run.stopped 记录失败原因与累计次数。
- 权限、认证、无效参数、额度耗尽只尝试 1 次。测试故意把这些错误的 retryable 标记设为真，类别白名单仍拒绝重试。工具权限及参数错误也只执行 1 次。
- 模型调用预算设为 2 时，连续临时失败以 model_budget 停止，实际只调用 2 次。工具预算为 1 时不会发起第二次工具尝试。超时循环在测试的有界等待内结束，取消退避会传播 CancelledError。
- 在真实 PostgreSQL 上，首次建单提交后注入连接丢失。图尝试 2 次，审批 ID、动作 key 与摘要保持相同，最终只有 1 条工单、1 条执行回执。写入 PermissionError 只调用 1 次，工单和回执均为 0。
- 浏览器通过本地受控限流 provider 提交实际 API 运行，显示三次失败、两次退避、停止原因 rate_limit，累计模型 3 次、工具和写入 0 次。错误和停止事件按各自类型显示。

完整离线门禁 80 项、真实 PostgreSQL 集成 39 项通过，前端格式检查和 TypeScript/Vite 构建通过。模型故障由 mock 和注入异常提供，写入和回执断言使用真实本地 PostgreSQL。

## 复现

运行 `python scripts/check_offline.py`。显式配置专用 TEST_DATABASE_URL，驱动为 postgresql+psycopg 且库名以 `_test` 结尾，运行 `python -m unittest discover -s tests/integration -p test_write_retry.py -v`，完整数据库回归使用 `python -m unittest discover -s tests/integration -v`。测试各自使用隔离 schema 并在结束后清理。

Python 调用方可通过 RetryPolicy 配置 1 至 3 次尝试及退避基数，通过 max_model_calls 配置模型尝试预算。预算在每次调用之前检查并递增，等待审批的 run 恢复时沿用检查点计数。模型 SDK 的 max_retries 为 0，重试由运行编排层统一执行。直接受控建单请求的回执恢复遵循 Day 19 的 key 约定。

浏览器夹具源码与 CLI 脚本保存在验证 JSON 的 browser 对象中。把 fixture_source 保存为 output/day20-runtime/server.py，设置 SUPPORTOPS_PERSIST_RUNS=0 并运行该脚本，前端 API_PROXY_TARGET 指向 http://127.0.0.1:8020，即可复现持续限流的页面日志。

## 失败边界与限制

线程中的数据库调用在等待超时后仍可能继续执行。写入重试通过同一审批 key 和事务回执核对结果。失败状态表示运行层已经停止继续尝试，实际已提交结果可通过原 key 查询。逻辑节点输出时才保存检查点，进程在节点中途退出可能重跑尚未落盘的尝试，保存计数反映已完成节点的执行记录。

本机原 TEMP 目录别名缺失，恢复指向项目 output/day8-runtime 的 junction 后启动原数据集群并完成验收。浏览器故障 provider 仅用于本地验收，包装脚本及截图保留在忽略的 output 目录。测试采用合成数据与固定本机演示身份，未调用付费 API。
