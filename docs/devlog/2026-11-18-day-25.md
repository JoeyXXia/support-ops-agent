## 失败修正

首次真实 stdio 冒烟以1退出：错误日志中的 datetime 先被转成 JSON 字符串，再用严格 Python 模型校验，导致 get_recent_errors 结果封装失败。实际定位验证了 JSON 模式失败、Python 模式成功；改为先校验 Python 对象，在协议边界再序列化，两个工具均通过。未放宽参数类型或业务授权。

安装源码签名核查同时确认 SDK2.3.0 的 MCPError 携带结构化 error 对象，异常变量为 exc 时使用 exc.error.code 读取协议码；据此修正初始客户端断言。早期 SDK 元数据类型探查与长行格式错误也已修正；最终门禁通过。验证 JSON 保存首次失败说明和后续成功输出，不将失败写成已通过。

依赖前后通过 pip list 比较，既有版本无变化；新增14个包的版本列表已保存。Windows 专用 marker 在 win32 为真、linux 为假，只代表标记计算，不冒充已执行 Linux 安装或远端 CI。

## 主要边界与取舍

本机受信任启动器可以选择种子主体，名称不是认证凭据；拥有本机进程/代码权限的人在信任边界内。这不是 HTTP 会话认证，也不是远程多用户安全承诺。一个进程固定一个主体，server 启动后不接受模型参数、请求元数据或工具描述改写身份。

只读注解是给 Host 的提示，不能代替服务器白名单和 ToolExecutor 授权。MCP 负责协议发现与调用，不代替登录、租户过滤、审批或事务幂等。stdout 仅放协议消息，错误诊断使用 stderr，不能随意 print 调试信息。

SDK 的低层 Server 不替我们执行广告中的参数 schema，真正校验仍由原 ToolExecutor 做；采用低层接口是为保留现有严格业务契约，避免自动包装产生不期望的类型转换。当前数据源仍是合成只读文件，未接外部生产系统。

客户端固定模块、目录与可执行文件，不接受任意命令、URL或 shell 片段；明确传递的环境不包含模型密钥和数据库 URL。等待保护只用于最小验收客户端，未注入挂死/强杀故障，不提前宣称完成 Day26 的 Agent 超时与权限传播。第三方 Host、旧协议兼容、远程 HTTP/OAuth、写工具和网页 Agent MCP 路径均未实现或未验收。
