# 产品范围与 Day 1 约束

日期：2026-10-22。依据仓库现有 `doc/planning/` 的三份计划；保留原路径，新增实现文档放在 `docs/`。

## 一句话目标

为虚构 SaaS CloudDesk 提供可追溯的技术支持：查询工作区状态、检索有依据的文档，解决不了时由用户批准后创建工单。

## 三条用户故事（最终目标，尚未实现）

1. 作为 CloudDesk 用户，遇到升级后 API 返回 429 时，我希望结合版本、配额和最近错误得到有出处的排查建议，避免盲目重试。
2. 作为求助用户，当问题无法自行解决时，我希望先查看准确的工单内容与目标工作区，再批准创建；重复批准不能重复建单。
3. 作为支持人员，我希望查看权限范围内的运行轨迹、引用和失败状态，从而接手问题；不能看到其他租户的数据。

## 五个不做项（本轮 8 周）

1. 任意代码执行、浏览器全自动操作和通用插件市场。
2. 完整计费系统或商业客户生产系统接入。
3. 多云、完整 Kubernetes 集群和微服务平台。
4. 知识图谱平台、模型训练或微调训练平台。
5. 把多 Agent、第二模型或复杂 UI 作为主线前置条件；这些仅在主线稳定后按实验价值取舍。

## 工程约束

- 单仓库、一个 Python/FastAPI 后端、React/TypeScript/Vite 前端；仅建立当前使用的目录。
- 今天只实现 `/health`、页面联通、格式检查和环境变量模板。无模型调用，无密钥要求，无数据库。
- 后续先手写 loop 再引入 LangGraph；PostgreSQL/pgvector、权限、审批、幂等按计划逐步加入。
- 身份和租户来自服务端可信上下文，不能信任模型自报身份；写操作须审批，副作用靠事务和唯一约束保证幂等。这些是未来约束，不是今天已完成能力。
- 使用自写或授权数据，明确 synthetic；不把 mock、回放或计划中的指标写成真实模型效果。
- `.env` 及变体全部忽略，只有无凭据的 `.env.example` 进入版本管理；不将密钥放入 `VITE_*`。
- 保留原始计划，不伪造提交或学习完成情况；提交推送按用户明确授权执行。
