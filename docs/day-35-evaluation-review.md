# 技术复盘 02 · 把评测拆成可复现的回归门禁

Day34 的开发集用同一份冻结数据从 24/60 提升到 29/60。增量来自四条套餐调用配额问法和一条打开引用流程。剩余 25 条行为失败、6 条覆盖缺口。把 48.3% 设为 PR 门槛会掩盖严重程度。一条越权读取失败应单独拦截，即使其他问答的通过率在上升。

## 每次 PR 检查什么

| 检查 | 要求的证据 |
| --- | --- |
| 确定性评分 | 缺工具、错误参数、超预算、缺工单或缺执行回执时评分失败。评分读取实测行为 |
| 权限 | 工作区由可信服务端身份限定。无权与不存在的响应一致。HTTP 运行和审批限保存的主体 |
| 幂等 | 并发、丢响应重试与事务回滚后，数据库里的工单和执行回执保持一致 |
| 整体回归 | 原有全量 Python、PostgreSQL、前端和浏览器门禁继续覆盖模块组合 |

门禁中安排快速定向步骤，失败时可以直接定位到评分、授权或写入契约。现有全量回归也会跑这些测试，带来少量重复时间，换取清晰的日志定位和统一的本地复现入口。

权限验证曾在独立进程中临时移除只读工具的租户过滤条件。原有负例产生一次断言失败，恢复后通过。这个实验说明当前测试对这处过滤条件敏感。幂等断言还需要数据库证据，因为 API 结果看起来成功时可能有重复写入。

## 发布前人工运行什么

手动工作流要求从 `main` 明确确认预算。它把三条冻结开发问题与对应的公开合成资料发给 OpenAI，核对固定格式答案，输出逐例通过、耗时与服务实际返回的 usage。场景覆盖套餐数值、月额度耗尽、资料不足。人工触发是在 [GitHub Actions](https://github.com/JoeyXXia/support-ops-agent/actions/workflows/live-evaluation.yml) 选择该工作流、`main` 与确认框。工作流使用专用 Actions secret `SUPPORTOPS_LIVE_EVAL_OPENAI_API_KEY`。凭据仅在评测步骤可用。 [GitHub 手动触发文档](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch)

单次工作流尝试最多发出三次串行请求，每次最多 1,200 字节提示词和 32 个输出 token，20 秒超时，首次 provider 错误即停止。重复手动触发或重新运行会重新使用这一预算。输入字节约束与供应商输出 token 上限是请求护栏，美元花费取决于计费和实际 usage。

这三条使用给定资料，只验证真实模型在受限 QA 上的格式和内容。Day34 的检索流程、工具选择、审批写入和端到端权限由各自的离线或数据库证据覆盖。当前没有本次真实模型分数或成本数据。

## 面试口述

每次 PR 都验证可重复且安全影响明确的契约。发布前人工选择是否运行付费的、小样本真实模型评测。失败分布比一个总分更能指导下一次修复。Day34 的高优先级信号是已有检索证据却弃答，以及几个故障场景缺少对应运行证据。
