# SupportOps Agent：面试与 AI 协作手册

配套：[总计划](./SupportOps-Agent-项目总计划.md) · [56 天每日计划](./SupportOps-Agent-56天每日计划.md)。

以下问题是根据项目能力设计的模拟追问，不声称是任何公司的真实面试题。先用自己的话回答，再让 AI 指出缺口。

## 1. 判断自己是否掌握了一个模块

每个重要模块用四级自检：

1. **知道**：能解释名词和用途。
2. **实现**：能找到代码，说明输入、输出、依赖与错误处理。
3. **验证**：能展示一个正常案例和一个反例，知道现有测试的限制。
4. **取舍**：能比较替代方案，拿数据或业务约束解释为什么这样做。

主线模块至少达到第 3 级；RAG、审批幂等、状态恢复争取第 4 级。选做模块诚实说明只是实验或初步接触。

## 2. 40 个项目深挖问题

### Agent 原理与编排

1. 这个任务为什么需要 Agent？哪些环节直接用代码或固定工作流更合适？
2. 手写 loop 的消息怎么组织？tool call ID 如何与返回结果对应？
3. 模型选错工具、填错参数、调用不存在的工具时各怎么处理？
4. 你如何定义停止条件？模型一直重试同一个工具怎么办？
5. 你为什么使用 LangGraph？用普通函数、数据库状态机能否实现？
6. checkpoint 保存了什么？重启后哪些节点可能再次执行？
7. 多 Agent 实验有什么实测收益？增加了多少调用、延迟与失败点？未实现时就说明设计思路与范围。
8. 一个新的模型 provider 接入时，除了 URL 和 key，还需要核对什么？

**证据**：原生 loop、状态图、工具 schema、异常测试、ADR、可选的单/多 Agent 实验表。

### RAG 与上下文

9. 为什么选择当前 chunk 边界与长度？有没有做对照？
10. Embedding 相似为什么不一定表示答案相关？
11. 错误码、产品版本号为什么可能需要关键词召回？
12. RRF 如何融合排序？为什么不同检索器的原始分数不能直接随便相加？
13. 重排改善了什么，增加了多少成本和延迟？什么时候关闭？
14. 检索不到、检索错版本、模型误读这三类问题如何区分？
15. 你如何验证引用支持答案，而不仅是引用 ID 存在？
16. 文档更新后，chunk、embedding、检索缓存、引用如何失效或保留版本？
17. 长对话摘要丢失关键信息怎么办？用户更正的事实怎么覆盖旧值？
18. 知识库、对话历史、长期记忆和缓存的作用域有什么区别？

**证据**：数据集、chunk 样例、消融报告、引用原文、版本更新和隔离测试。

### 权限、审批与可靠性

19. 为什么不直接让模型传入任意 tenant_id？可信身份来自哪里？
20. 用户批准后动作参数被修改怎么办？批准过期了怎么办？
21. 重复点击批准、网络重试、worker 重启分别如何避免重复建单？
22. 工单已写入但客户端没收到响应，重试时会发生什么？
23. 为什么不能简单承诺 exactly-once？你的幂等保证覆盖到哪里？
24. 进程被杀死后，任务如何重新被领取？lease 与幂等怎样配合？
25. 取消发生在工具调用中或写入之后，能保证什么？
26. SSE 断线重连如何补事件？如何避免新建第二个任务？
27. 多租户隔离除了 SQL 查询，还需要检查哪些缓存、日志、引用和事件通道？
28. prompt injection 防御为什么不能只靠 system prompt？
29. MCP 与普通函数调用、HTTP API 有什么区别？协议是否自动提供业务授权？
30. 重试、超时、并发上限、限流、背压各解决哪一种故障？

**证据**：数据库约束、事务代码、审批参数摘要、故障注入记录、权限反例。

### 评测、性能与交付

31. 你的成功率分母是什么？回答对但实际没有建工单算成功吗？
32. Hit@5 和 Recall@5 有什么区别？你的相关片段标注完整吗？
33. 为什么要分开发集和测试集？相同问题换个说法分到两边有什么风险？
34. AI 生成样例有哪些偏差？你如何人工审核？
35. LLM judge 和人工评分不一致时如何处理？
36. p50、p95、首个状态事件和首个回答 token 分别反映什么体验？
37. mock 压测成绩能说明什么，不能说明什么？
38. 为什么每次请求成本下降，成功任务成本仍可能上升？
39. 如果用户增加 100 倍，先测哪里、改哪里？有什么证据支持？
40. 哪些代码由 AI 协助？你如何证明自己知道它在做什么？

**证据**：固定配置的报告、逐案例结果、人工标签、压测脚本、PR 与开发记录。

## 3. 项目之外必须补的基础

| 周 | 每天约 25–30 分钟的基础主题 | 周末独立完成 |
|---|---|---|
| 1 | Python 容器、异常、迭代器、装饰器、typing、测试替身 | 写一个带参数校验的工具注册器 |
| 2 | SQL JOIN、索引、唯一键、事务、EXPLAIN | 写 3 条查询并解释索引选择 |
| 3 | asyncio、超时、取消、信号量、阻塞 I/O、线程/进程 | 写有限并发任务执行器，处理单任务异常 |
| 4 | HTTP、SSE、认证、授权、Cookie/token、CORS | 解释一次完整流式请求和鉴权路径 |
| 5 | tokens、embedding、attention/Transformer 直觉、采样、上下文、RAG 与微调区别 | 不看笔记讲清一个工具调用请求的全过程 |
| 6 | 缓存、幂等、队列、重试、连接池、日志指标 | 分析一次重复写与一次队列积压 |
| 7 | 时间/空间复杂度、哈希、堆、队列、LRU/TTL | 完成一个缓存或 top-k 练习并说明边界 |
| 8 | 综合 SQL、编码、系统设计、项目表达 | 两次 45 分钟模拟面试 |

算法练习选 12–20 道与常见结构相关的题，确保能独立写、解释复杂度、处理边界。如果目标是强算法笔试的大厂岗位，应另外增加系统刷题时间；这个安排只是项目期间的基础维护量。

## 4. 每天可复制的 AI 协作提示词

### A. 开工拆解

```text
今天做 SupportOps Agent 的 Day NN：[贴任务]。
先阅读当前相关代码与项目约束，不要直接扩大范围。
给出：当前实现摘要、最小修改方案、涉及文件、3–5 个可观察验收条件、最可能失败的边界。
把工作拆成 2–3 个可独立审查的改动。
不引入今天用不到的服务和框架；不填写未经测量的结果。
```

### B. 实现一小步

```text
现在只实现：[一个小目标]。
已确定接口：[接口]；约束：[权限、超时、幂等或性能要求]。
复用现有项目结构。对与本次改动有关的风险添加有意义的验证。
完成后说明：改了什么、为什么、执行过哪些验证、尚未解决的问题。
不要把 mock 结果当作真实模型结果，不要修改不相关文件。
```

### C. 审查 AI 的代码

```text
请审查当前 diff，重点找真实缺陷：
权限是否可以绕过；副作用是否可能重复；错误是否被吞掉；async 路径是否阻塞；
缓存是否串租户或版本；测试是否只是重复实现；日志是否记录不必要的敏感内容。
每条发现给出触发条件、影响、相关位置与最小修复建议。
没有足够证据的问题请标为待确认，不编造漏洞。
```

### D. 解释与口述验收

```text
根据今天实际代码，问我 5 个递进问题：用途、数据流、一个失败场景、替代方案、实现边界。
一次只问一个，等我回答后再追问；不要先给标准答案。
最后指出我讲不清的地方，并定位到需要重读的代码。
```

### E. 实验报告

```text
根据这份原始实验结果生成 Markdown 报告：[结果路径或内容]。
必须包含配置、样本量、基线、实际数值、失败类别、限制和下一步。
分清事实与推测；没有显著提升就直说；不得补造数据。
不要把开发集结果称为未见测试集结果。
```

### F. 写提交说明

```text
根据当前 diff 建议 2–3 个逻辑清晰的提交边界与英文 commit message。
每个提交说明实际改变的行为，避免空提交和为了数量切碎代码。
不要直接 push；先给出待提交文件与对应说明，由我检查。
```

这些是你未来开发时可采用的工作习惯，不要求本次计划阶段创建仓库、连接模型或提交任何代码。

## 5. 一个真实开发日的提交例子

以 Day 19 幂等为例：

```text
fix: make approved ticket creation idempotent
test: cover concurrent approval and lost responses
docs: explain ticket creation failure windows
```

三个提交分别承载实现、关键验证、设计解释。若当天只有一项真实修改，一个提交即可。不要空提交、倒填日期或复制整套项目后伪造渐进记录。

建议 PR 描述：

```markdown
重复审批或响应丢失后的重试原先可能创建多条工单。
现在使用逻辑动作 ID 的唯一约束与事务；重试返回已存在的工单。

验证：顺序重复、并发重复和写入后响应丢失三个场景均只产生一条工单。
限制：当前保证仅覆盖本项目数据库内写操作；外部系统需要另行设计幂等接口或补偿。
```

若在 GitHub 使用 squash merge，细粒度提交可能被合并。学习阶段可保留有意义的提交历史；选择合并策略应服务代码可读性，不把贡献格子当作能力指标。

## 6. 简历表述模板

只在完成后填写，所有数字以仓库报告为准：

> 独立开发 SupportOps Agent，基于 Python/FastAPI、LangGraph 和 PostgreSQL/pgvector，实现知识检索、工具调用、人工审批与工单处理流程，并提供容器化部署和在线演示。

> 构建包含 [N] 个案例的分组评测集，对向量召回、混合检索和重排进行对照实验；在 [明确评测分区与配置] 下，Hit@5 为 [实测值]，任务成功率为 [实测值]，保留逐案例失败分析。

> 为异步任务实现持久状态、有限重试和业务幂等，验证重复审批、响应丢失、worker 重启等场景；在 [硬件/并发/样本量] 下测得端到端 p95 为 [实测值]。

不要写“服务上万用户”“生产级金融系统”“准确率 99%”“显著降低成本”等未经证实的描述。明确它是个人项目与合成数据演示。

## 7. 面试讲述结构

### 90 秒版本

“我做的是一个面向 SaaS 技术支持的 Agent。用户提出问题后，它会查询工作区状态、检索产品文档，给出带引用的建议；需要建单时展示动作供用户批准。我的重点是让流程可验证、可恢复：工具参数和权限由后端检查，写操作通过数据库约束保证业务幂等，检索和最终任务效果有固定评测集。我做过 [实际实验]，结果是 [实测结论]。目前主要限制是 [真实限制]。”

### 5 分钟版本

1. 30 秒业务目标与用户流程。
2. 60 秒架构：模型、工具、状态、数据库与 UI 如何连接。
3. 90 秒最难的问题：审批/幂等或恢复，包含具体失败场景。
4. 60 秒实验：基线、改动、数据、结果与限制。
5. 60 秒演示和下一步。

面试官追问时优先打开实际报告、相关代码和失败案例。框架名只是入口，能解释取舍和边界才体现掌握程度。

## 8. 最终自测

- [ ] 不看 AI 答案，解释主流程以及所有工具的权限。
- [ ] 现场画出正常、待审批、失败、恢复四种路径。
- [ ] 找到一条真实失败记录，并说明归因与修复证据。
- [ ] 说明一个没有产生收益的实验，以及为什么舍弃。
- [ ] 独立实现一个小工具或修复一个边界缺陷。
- [ ] 讲清哪些来自 AI 建议、哪些由自己判断和验证。
- [ ] 区分已经实现、已验证、实验性质、尚未实现四种状态。

完成这些之后，项目会成为有内容可深挖的求职作品；录用仍取决于岗位匹配、基础能力与面试表现。
